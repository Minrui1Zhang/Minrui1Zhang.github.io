Agent Lightning v1.0: Towards Harnessed Agentic RL挑战 01 · Token 前缀连续性

文本延续，不等于 token 前缀连续

Harness 分别构造每次请求；trainer 只看到 (pᵢ, aᵢ) 调用对，不能假设它们天然组成一条连续 token 轨迹。

(pᵢᵗᵉˣᵗ, aᵢᵗᵉˣᵗ) ⪯ pᵢ₊₁ᵗᵉˣᵗ　⇏　(pᵢᵗᵒᵏ, aᵢᵗᵒᵏ) ⪯ pᵢ₊₁ᵗᵒᵏ

文本前缀成立，token 前缀也可能失效：图中 h + aving 被重分为 hav + ing，旧响应无法原样拼入下一次训练序列。

[L] §2 开头, Eqs.2–6; §2.1, Eqs.8–9, Fig.3, pp.4–5
讲者备注

⪯ 表示完整前缀。p 是实际输入 prompt，a 是原始采样的响应。训练系统必须保留每次动作真正采样时的条件。上下文压缩、子智能体也可能直接改变历史，使文本级前缀本身就不成立；Figure 3 则强调即使文本不变，也不能推导出 token 级连续性。下一页保留原有三种失效机制的解释。

Agent Lightning v1.0: Towards Harnessed Agentic RL挑战 02 · 处理方法

为什么先在 rollout 层计算优势？

01

按样本统计，会重复计奖

同题两次 rollout，一次成功、一次失败。成功任务若拆成三段，按样本统计的奖励均值会从 0.50 变为 0.75。

02

切分不应改变优势基线

重分词、子智能体和上下文压缩只是执行与样本构造方式，不应让某次任务因片段更多而更影响整组统计。

先让每个 rollout 的奖励只参与一次组内统计，计算优势后再分配给其样本，使优势基线不受切分数量影响。

[L] §2.2, Fig.4, pp.6–7
讲者备注

例子中，rollout 层奖励均值为 (1+0)/2=0.50；若成功轨迹拆成三个样本、失败轨迹保留一个样本，按样本统计变成 (1+1+1+0)/4=0.75。差异来自样本切分，而不是任务结果变化。论文因此选择先在 rollout 层计算优势，再让该 rollout 的样本继承优势。该处理纠正组内统计单位，不等于已经解决不同分支的细粒度信用分配，也不替代下一页讨论的损失归一化。

Agent Lightning v1.0: Towards Harnessed Agentic RL挑战 04 · 动态样本调度

动态样本如何映射到固定 GPU？

样本数量与长度只有在 harness 执行、构造样本后才确定，而 GPU 数量及并行配置固定；相同 rollout 数不代表相同 token 负载或显存需求。

调度环节关键约束
展平 / 打包每条 sample 保留 rollout ID 与 prompt-group ID，改变物理布局不改变统计归属。
并行分配 / micro-batch按 token 工作量均衡 GPU 负载，同时保持正确的 rollout 权重。
Optimizer update同一 rollout 的全部样本进入同一次参数更新，避免不同片段在不同策略版本下被评估。

打包与分配可以调整，但不能改变任务权重或拆散更新边界；同一次 update 可以包含多个 micro-batch。

[L] §2.4, Eq.17
讲者备注

重分词、上下文压缩与子智能体使样本数量动态变化，因此不能仅凭 prompt 数或 rollout 数提前规划张量行数与 micro-batch。Eq.17 要求展平后仍保留样本的 rollout 与 prompt-group 归属。一个 rollout 的样本可通过多个 micro-batch 累积梯度，但应在同一次 optimizer update 内完成，避免 within-rollout policy skew。这里归纳论文对后端的约束，不声称提出了新的最优负载均衡算法。

Agent Lightning v1.0: Towards Harnessed Agentic RL系统设计 · 网络可靠性

网络中断后，重试如何不污染训练？

执行与训练分离后，两条链路都可能中断：Trainer / Controller 到 Gateway，以及 harness 经代理到模型推理端。两类请求需要分别处理重试。

01

控制 API：保证幂等

Rollout API 重复调用任意次数，效果与调用一次相同；网络失败后可以重试，避免重复操作破坏任务状态。

02

模型生成：组样本时去重

LLM 重试可能生成不同回答，不能直接视作幂等。在同一 rollout 内，对 prompt 完全相同的 model_request 事件只保留最后一次。

控制请求靠幂等保护状态；重复生成靠事件去重，避免把重试或已被替代的调用重复纳入训练。

[L] §3.2 Network Issues, p.10
讲者备注

去重发生在 Customized Trainer 组装训练样本时，范围是同一次 rollout 内完全相同的 prompt，保留最新调用。不能将此规则扩大为跨 rollout 去重，否则会删除同题多次采样的正常探索。LLM 的重新生成并不保证与上次响应相同，所以论文明确将控制 API 的幂等与模型调用的去重分开。

过滤这类退化组，再采集额外轨迹，增加具有差异性奖励和有效策略梯度的样本比例。

Efficient Agentic Reinforcement Learning with On-Policy Intrinsic Knowledge Boundary Enhancement研究背景 · 现象

RL 训练为何让模型越来越依赖工具？

Cognitive offloading 是什么？

本可依靠参数知识作答却调用工具，或本可少量调用却反复检索；模型越来越把求解过程外包给工具，知识边界随之模糊。

冗余调用带来什么后果？

既浪费计算、增加推理延迟，也可能引入误导性检索噪声，覆盖正确的内部推理，使原本能答对的问题变成错误答案。

分析对象是早期以 0 / 1 / 2 次调用答对的样本，并非全部训练数据；图中现象不能单独证明参数知识被遗忘。

Efficient Agentic Reinforcement Learning with On-Policy Intrinsic Knowledge Boundary Enhancement问题与核心

Reward shaping：把工具效率写进奖励，够吗？

不再只按最终答案是否正确给分，而是把工具使用的效率或调用模式加入奖励，让 RL 同时学习“答得对”和“用得省”。

答案正确性奖励+工具效率奖励 / 调用惩罚→据调整后的奖励更新策略

现有方法怎么做？

OTC-PO 加入工具生产率奖励项；β-GRPO 引入置信度阈值；HiPRAG 使用分层过程奖励评价每步工具调用。

不足在哪里？

整体奖惩较粗，模型可能为额外奖励一概少用工具，连必要调用也被抑制，出现 reward hacking 与准确率下降；逐步评价又可能依赖外部模型或 API。

关键缺口：难以逐题区分必要与冗余调用，也难以跟随训练中不断变化的知识边界。

[K] §1 Introduction, §2 Related Work, pp.2–3
讲者备注

流程是 reward shaping 的概念示意，不是三种基线共用的精确奖励公式。论文将 OTC-PO 描述为引入 tool-productivity 项，β-GRPO 为引入置信度阈值，HiPRAG 为逐步评价的分层过程奖励。粗粒度整体工具奖惩可能诱导无差别压低调用；逐步评价方法则可能增加外部模型/API 开销。这里概括的是论文对已有方法的批评，不表示所有 reward shaping 在任何设置中都必然失败。后续 AKBE 通过当前策略双路径探测与辅助监督提供实例级信号，而不是修改基础任务奖励。
