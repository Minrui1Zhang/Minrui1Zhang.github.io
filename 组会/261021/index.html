Agent Lightning v1.0研究背景

训练循环的控制权，发生了变化

01

传统范式

Agent Lightning v1.0问题与核心

接上模型 API，就能正确训练吗？

01

问题

harness 掌控交互；训练器只看到一系列模型请求与回答。

02

难点

03

核心

保留真实采样条件，并以 rollout 作为优势与归一化的统计单位。

Agent Lightning v1.0系统设计

harness 管执行，trainer 管学习

Trainer 发起任务→Controller 启动 harness→Gateway 记录调用→Adapter 构造样本

用 rollout ID 串起请求、奖励和日志；代理保存真实 token 与 log probability。

[L] p.1 Fig.1; pp.9–11 §3
讲者备注

控制平面采用持久状态和事件记录；Controller 是尽力而为的最终一致性。动态打包可以改变数据位置，但不能改变统计归属；同一 rollout 的样本应处于同一次 optimizer update。

Agent Lightning v1.0系统设计 · 组件

三个组件，协调一次完整任务

组件输入与职责向下游交付
API Gateway保存 rollout 状态与事件；代理模型 API精确 token、log probability、调用与奖励记录
Rollout Controller轮询期望状态，启动本地进程或 K8S Job外部 harness 的执行状态与日志
Customized Trainer注册模型与任务；等待完成并读取事件Sample Adapter 构造样本，随后优化参数

Gateway 是生命周期状态的事实来源；Controller 用 reconciliation loop 驱动执行。

[L] §3, Appendix A
讲者备注

本地进程池与 Kubernetes 是可替换的执行后端。控制 API 幂等，执行控制采用尽力而为的最终一致性。

Agent Lightning v1.0系统设计 · 运行

同一组 GPU，交替服务采样与更新

积累足量已完成 rollout→暂停接收新推理，排空在途请求→共享 GPU 更新权重→恢复请求与采样

不必等待整批最慢任务完成；harness 的下一次请求由 Gateway 暂停与恢复。

[L] §3.1, Fig.6
讲者备注

同卡异步通过时间复用共享 GPU，不表示推理与更新在同一 GPU 上无条件同时执行。跨阶段长任务带来的策略版本仍需记录。约 2× 是论文配置下的结果。

Agent Lightning v1.0关键细节 01

文本相同，不代表 token 相同

01

风险

把下一次提示强行换成旧 token，会改变真实采样条件。

02

处理

只在精确 token 前缀匹配时合并；不匹配就开启新样本。

合并率不是目标：先保证条件正确，再复用计算。

[L] pp.3–6 §2.1, Fig.3
讲者备注

论文称条件不一致为 off-policy stitching；它不同于普通的行为策略落后于当前策略。独立训练保留真实条件，但会重复计算共享前缀。

Agent Lightning v1.0挑战 01 · 成因与边界

为什么重新分词会改变训练条件？

01

模板并非可拼接

对完整对话重新套 chat template，可能增删分隔符或历史 <think> 标记。

02

Decode → Tokenize 漂移

同一 having 可由 h + aving 或 hav + ing 组成；文本一致并不保证 token ID 一致。

03

输出后处理

工具协议可能修复、规范化并重新序列化 JSON，使下一次上下文连文本都发生变化。

(pᵢ, aᵢ) ⪯ pᵢ₊₁ 仅当精确 token 前缀成立，才安全合并

强换成缓存 token 会改变下一条动作的条件，形成 off-policy stitching。

[L] §2.1, Eqs.9–14
讲者备注

独立训练每次调用保证其采样条件，但重复计算前缀。论文选择保守合并；这里的偏差来自条件拼接，不只是策略参数陈旧。

Agent Lightning v1.0关键细节 02

拆成几段，不该改变优势基线

成功 rollout · reward = 1

sample 1sample 2sample 3

失败 rollout · reward = 0

sample 4
01

按 sample 统计

奖励均值变成 (1+1+1+0) / 4 = 0.75。

02

按 rollout 统计

奖励均值为 (1+0) / 2 = 0.50，再关联到各样本。

[L] p.7 §2.2, Fig.4
讲者备注

这里展示均值偏移，不把 mean-centered reward 当作完整 GRPO 标准化优势公式。先计算 rollout 层组统计，避免样本构造改变基线；分支之间如何做信用分配仍未解决。

Agent Lightning v1.0挑战 02 · 处理方法

优势在 rollout 层计算，再广播给样本

Aρ = (Rρ − μg) / (σg + ε)
同题多次 rollout→每次奖励只统计一次→计算组内 μg、σg→各 sample 继承 Aρ

避免“切得越多，越影响基线”；它还没有解决分支之间的细粒度信用分配。

[L] §2.2, Fig.4 · 公式为组相对优势的记号化说明
讲者备注

g 为同一 prompt 的 rollout 组；ε 是数值稳定项。所有样本继承同一 rollout 优势是本文设计选择。

Agent Lightning v1.0挑战 03 · 目标公式

先在任务内部平均，再在任务之间平均

L = (1 / |B|) Σρ [ (1 / Tρ) Σⱼ Σₜ mρⱼₜ ℓρⱼₜ ]
01

Tρ 统计什么？

该 rollout 所有样本中参与优化的生成 token 数；prompt 与环境观察不参与动作损失。

02

改变切分不改变权重

同一任务从一段拆成三段，仍只占一个 rollout 的平均权重；长短任务也保持任务等权。

[L] §2.3, Eqs.15–16, Fig.5 · 公式为等价记号
讲者备注

B 是 rollout batch，m 是生成 token mask。此目标是论文选择，不是任何任务都必须使用的唯一归一化。

Agent Lightning v1.0挑战 04 · 问题

样本数未知，GPU 并行配置却固定

固定数量的任务→harness 完成执行→才知道 sample 数和长度→分配至固定 GPU workers
01

工作量难预估

压缩与子智能体会改变样本数；相同 rollout 数不能保证相同 token 量或显存需求。

02

更新边界不能随意切

若同一 rollout 的不同片段进入两次 optimizer update，它们会在不同策略参数下被评估。

调度既要均衡 token 工作量，也要保留 rollout 的统计与更新边界。

Agent Lightning v1.0挑战 04 · 约束

物理打包可以变，统计归属不能变

Sρ,ⱼ → (sample, rollout_id = ρ, prompt_group_id = gρ)
调度环节必须保留的语义
Flatten / packing展平后仍能追溯所属 rollout 与 prompt group
Data parallel / micro-batch按 token 负载分配；保持正确的 rollout 权重
Optimizer update一个 rollout 的全部样本进入同一次参数更新

同一次 update 可以有多个 micro-batch；micro-batch 与 optimizer update 不是一回事。

AKBE论文 03

什么时候，该让模型自己回答？

Efficient Agentic Reinforcement Learning with On-Policy Intrinsic Knowledge Boundary Enhancement

Dingwei Chen 等 · Tencent / CUHK / SMBU · 2026.05

AKBE：用当前策略的成功路径，学习何时需要工具。

[K] p.1, arXiv:2605.26952v1
讲者备注

本页围绕标题所示问题展开讨论。

AKBE问题与核心

只奖励答对，可能越学越爱搜索

01

问题

最终正确性奖励，无法区分必要调用与冗余调用。

02

直接惩罚调用？

容易连必要工具一起压制：调用更少，答案却更差。

03

核心

每题同时试“有工具”和“无工具”，再选择合适的成功轨迹。

优化目标是更合理地使用工具，而不只是少用工具。

[K] pp.1–3, §§1–3
讲者备注

论文将过度依赖外部检索称为 cognitive offloading。Figure 1 跟踪早期已正确样本，不能把其中比例解释为全部训练数据。

AKBE研究背景 · 现象

已能回答的问题，仍可能逐渐依赖搜索

01

奖励的盲点

有工具和无工具都答对时，二元正确性奖励没有偏好；冗余搜索同样可以获得奖励。

02

边界逐渐模糊

反复通过搜索成功，模型可能更多地外包推理，减少调用内部知识的机会。

图中的分析对象是早期已正确样本；不能当成全部训练集的总体比例。

[K] §1, Fig.1
讲者备注

作者用 cognitive offloading 解释所观察行为。图不能单独证明模型参数知识被遗忘。

AKBE方法概览

当前策略，双路径探测

同一个问题→有工具 / 无工具采样→判断正确性→最多选择一个目标
[K] pp.3–5, Algorithm 1, Fig.2
讲者备注

WT 与 NT 表示对应路径是否至少出现一个正确样本。基础 RL 继续使用有工具轨迹，辅助监督最多每题选一条。无额外教师模型。

AKBE架构 (a) · 双路径探测

同一问题，同一当前策略，两种工具条件

WT = 𝟙[∃ 有工具轨迹答对]　 NT = 𝟙[∃ 无工具轨迹答对]
01

With-tool：探索外部帮助

采样 Gwt 条轨迹，保留任务奖励与调用数；这些轨迹用于基础 RL。

02

No-tool：探测内部能力

关闭工具，采样 Gnt 条回答；它们用于判断边界和构造辅助目标。

[K] §4.1, Eq.4, Algorithm 1
讲者备注

两条路径由同一个当前策略产生，不需要更强的外部教师。WT/NT 判断是每题每步重新进行的有限采样估计。

AKBE架构 (a) · 估计含义

知识边界是随策略变化的采样估计

KB(q, πθ) = NT
01

观察到成功

NT = 1：本轮至少存在一条正确无工具路径，为减少冗余调用提供证据。

02

没有采到成功

NT = 0：在本轮预算内未找到正确路径；可能是知识不足，也可能只是采样遗漏。

03

下一步重新判断

更新策略后重新双路径采样；同一道题可能从 Tool-dependent 转为 Efficiency。

边界不是预先固定的题目难度标签，也不是一个独立的工具路由分类器。

[K] §4.1–4.3
讲者备注

论文将 KB=0 操作性解释为需要外部工具；讲解时保留有限采样限制，避免把它等同于绝对能力边界。

AKBE监督选择

四种情况，分别给出信号

有工具成功无工具成功监督目标目的
是否调用最少的正确工具轨迹保留必要工具
是是随机一条正确无工具轨迹减少冗余调用
否是随机一条正确无工具轨迹纠正有害工具路径
否否不加辅助监督保留基础 RL

“无工具失败”只表示本轮未采样到成功，不等于模型绝对不会。

[K] pp.3–5, Algorithm 1, §4.2
讲者备注

分别为 Tool-dependent、Efficiency、Hallucination、Both-wrong。最少调用是在采样到的正确轨迹中取最小，不是全局最优；并列时随机选取。

AKBE架构 (b) · 监督构造

正确轨迹中，选择最合适的一条

01

保住必要工具

只有 WT 成功：在答对的工具轨迹中选 TC 最小的一条；相同最小值随机打破并列。

02

优先无工具成功

只要 NT 成功，就随机选择一条正确无工具轨迹；若两边都失败则不选辅助目标。

每题最多一个辅助目标，三类成功信号分别保护必要调用、减少冗余、纠正有害路径。

[K] §4.2, Algorithm 1
讲者备注

AKBE架构 (c) · 动态监督

为什么静态成功轨迹不够？

01

当前能力要匹配

后期强策略能无工具答对的题，早期弱策略可能仍需搜索；固定后期数据可能过早抑制工具。

02

在线重建目标

每个训练步都用当前策略重新选择成功路径，辅助监督与能力边界同步变化。

03

开销也要计算

主要配置 Gwt = 16、Gnt = 8，最多 6 次工具调用；无工具采样没有检索等待，但仍消耗生成算力。

On-policy 指监督来源随当前策略更新；不代表额外采样成本为零。

讲者备注
